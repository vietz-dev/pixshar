## 2026-07-05
* **Change**: Archive parts are now **incremental and immutable**. A build no longer rewrites the whole archive on every upload — it appends only newly-uploaded photos as new parts and rebuilds a part in place only when a photo inside it is deleted. Updated [archive generation](/architecture/archive-generation.md), [multi-part archive decision](/decisions/multi-part-archive.md), [download jobs](/data-model/download-jobs.md).
* **Change**: Part identity: each part carries a `membershipSig` (content identity for client download-tracking) and a `generation` (versioned S3 key for old/new coexistence during a rebuild). New `DownloadArchivePartEntry` join table records durable part membership.
* **Change**: Admin controls split — `POST /download/build-now` (skip debounce, keep FIFO) and `POST /download/rebuild-all` (membership-preserving full rebuild) replace `POST /download/build`.

## 2026-07-11
* **Promotion**: [Download-Varianten](/decisions/download-variants.md) shipped — moved from `concepts/` to a Decision. Every event now always builds **two** archive variants, Kompakt (`DISPLAY`, from the display images) and Original (`ORIGINAL`), as two independent per-`quality` `DownloadJob`s. Kompakt is the guest default (opt-in Original); the Kompakt job is created lazily for pre-existing events.
* **Change**: `DownloadJob` gains `quality` with `@@unique([eventId, quality])`; parts inherit the variant; S3 archive keys gain a `{quality}-part-…` segment (legacy `gallery-part-…` = ORIGINAL). Updated [download jobs](/data-model/download-jobs.md), [storage](/architecture/storage.md).
* **Change**: The build trigger fans out over both variants (upload enqueues both; deletion stales both), the FIFO claim key is now `(event, quality)`, and the orphan sweep is variant-scoped. Updated [archive generation](/architecture/archive-generation.md).
* **Change**: `GET /api/gallery/:slug/download` returns both variants in one payload (Kompakt default); admin status/build-now/rebuild-all/cancel take a `?quality=` selector; the admin panel renders two per-variant panels and the guest page a Kompakt/Original toggle. Updated [gallery API](/api/gallery-api.md), [admin API](/api/admin-api.md).

## 2026-07-12
* **Rewrite**: [Archiv-Lebenszeit](/concepts/zip-ttl-storage.md) (vormals „ZIP TTL Storage") auf den beschlossenen Stand gebracht und als `specced` markiert — Tickets PIXSHAR-1 … PIXSHAR-9 in Plane. Der Dateiname bleibt vorerst, um die vier verlinkenden Dokumente nicht zu brechen; beim Promoten zur Decision wird umbenannt.
* **Refutation**: Der bisherige Vorschlag **S3-Lifecycle-Regeln** ist widerlegt — S3-Expiry ist altersbasiert, nicht zugriffsbasiert, und würde aktiv genutzte Archive löschen. Stattdessen ein anwendungseigener Idle-Reaper (CAS-Claim, erst Objekte löschen, dann Status kippen).
* **Change**: Der **eager Erstbau entfällt**. Archive entstehen nur noch auf explizite Anforderung (Gast-Button bzw. Admin-Pre-Warm); Uploads halten lediglich eine bereits lebende Variante aktuell („lazy beim Erschaffen, eager beim Aktuellhalten"). Betrifft [archive generation](/architecture/archive-generation.md) und [Download-Varianten](/decisions/download-variants.md), sobald implementiert.
* **Change**: Neues Zugriffssignal — Part-Links laufen über einen Redirect-Endpoint, der `lastDownloadedAt` stempelt und mit 302 auf eine frisch signierte S3-URL zeigt (Bytes weiterhin direkt aus S3, Presign-TTL 1 h → 15 min). Ohne ihn kann die API einen echten Download nicht von einem Seitenaufruf unterscheiden.
* **Change**: Foto-Löschung entfernt das S3-Objekt der betroffenen Parts **sofort** (statt das alte Objekt bis zum Reconcile weiter auszuliefern) — unter dem Lazy-Modell wäre dieses Fenster sonst unbegrenzt. Korrektheits-, keine Kostenregel.
* **Creation**: Monitoring-Konzept für die TTL-Justierung — Per-Event/Per-Variante-Zählstände in `DownloadJob` (überleben Pod-Restarts), als DB-gestützte Gauges exportiert (Kardinalität auf 30-Tage-aktive Events gedeckelt), plus Histogram `pixshar_archive_expiry_to_rebuild_seconds` und eine Grafana-Row „Archive Lifecycle" in **beiden** Dashboard-JSONs.

## 2026-07-12 (implementation)
* **Promotion**: [Archiv-Lebenszeit](/decisions/archive-lifetime.md) shipped (branch `feat/archive-lifetime`, PIXSHAR-1…10) — moved from `concepts/zip-ttl-storage.md` to a Decision, following the same promotion pattern as [Download-Varianten](/decisions/download-variants.md). The concept file is removed (not stubbed); its content lives on as the decision record. Updated cross-references in [KEDA Worker Scaling](/concepts/keda-worker-scaling.md) and [Cloud-Export](/concepts/cloud-export-google-dropbox.md), and removed the entry from [concepts index](/concepts/index.md).
* **Change**: Archive builds are now **lazy for both variants, not just legacy Kompakt**. `requestBuild` (`services/downloadJob/triggers.ts`) is the single entry point that creates a `DownloadJob`, called only by the new guest endpoint `POST /api/gallery/:slug/download/request?quality=` and the admin `build-now` pre-warm action. `GET /api/gallery/:slug/download` no longer has an `ensureJob` side effect — opening the download page is a pure read. Uploads append only to variants that are currently alive (`READY`/`DEBOUNCING`/`QUEUED`/`BUILDING`) via `triggerDebounceAllVariants`; an `EXPIRED` or nonexistent variant is never revived by an upload. Updated [archive generation](/architecture/archive-generation.md), [Download-Varianten](/decisions/download-variants.md) (added an update note — its "always built eagerly" framing no longer holds), [Gallery API](/api/gallery-api.md), [overview](/overview.md).
* **Creation**: `DownloadJobStatus.EXPIRED` and `DownloadArchivePart.status = "EXPIRED"` — the row/membership survive, the S3 object is reclaimed. New `DownloadJob` columns `lastDownloadedAt`, `readyAt`, `expiredAt`, `expiryCount`, `rebuildCount`; migration backfills `lastDownloadedAt = now()` for every existing `READY` job (full TTL grace period at deploy). Updated [Download Jobs data model](/data-model/download-jobs.md).
* **Creation**: New guest endpoint `GET /api/gallery/:slug/download/part/:index?quality=` — the real-download signal. Stamps `lastDownloadedAt` on the job, then 302s to a freshly presigned S3 URL; part links in the payload point here instead of at S3 directly. Presign TTL dropped 1 h → 15 min (`ARCHIVE_PART_PRESIGN_SECONDS`) since S3 validates only at request start. Updated [storage architecture](/architecture/storage.md), [Gallery API](/api/gallery-api.md).
* **Creation**: The idle reaper (`services/downloadJob/reaper.ts`) — a CAS-claiming (`updateMany WHERE status = 'READY'`) periodic sweep, safe under multiple replicas, disabled entirely at `DOWNLOAD_ARCHIVE_TTL_DAYS=0`. New admin endpoint `POST /api/events/:id/download/release?quality=` runs the identical `expireArchive` effect on demand. **The ordering rule**: both the reaper and photo-deletion's `expirePartsForDeletedPhotos` flip rows to `EXPIRED` in the same transaction as the CAS claim *before* deleting S3 objects — never the reverse — so a crash can only ever leave `EXPIRED` rows with possibly-live objects (harmless; the builder's orphan sweep reclaims them), never a `READY` row pointing at a deleted object. A code-review fix commit (`8f2ddcd`) corrected an initial version that had this backwards. Updated [archive generation](/architecture/archive-generation.md).
* **Change**: Photo deletion (`services/downloadJob/deletion.ts`) now expires the affected parts' S3 objects **immediately** (across both variants) instead of marking them `STALE` for a later debounced reconcile — under the lazy model that reconcile might never come, which would leave a deleted photo downloadable indefinitely. A part emptied of its last photo is deleted outright rather than kept as an empty `EXPIRED` row. Updated [archive generation](/architecture/archive-generation.md), [Download Jobs data model](/data-model/download-jobs.md).
* **Creation**: Seven `pixshar_archive_*` Prometheus metrics (`apps/api/src/lib/metrics.ts`) and a new "Archive Lifecycle" Grafana row in both `monitoring/grafana/dashboards/pixshar-overview.json` and `helm/pixshar/dashboards/pixshar-overview.json`. Per-event gauges (`pixshar_archive_expiries`, `pixshar_archive_rebuilds`) mirror DB counters at scrape time (30-day activity cutoff bounds cardinality); the rest are in-process counters/histograms. Documented fully in [Archiv-Lebenszeit](/decisions/archive-lifetime.md).
* **Refactor** (not doc-visible, noted for context): `services/downloadJob.ts` split into `services/downloadJob/{status,triggers,poller,admin,payload,builder,expiry,reaper,deletion}.ts`. The pure decision (`archiveExpiresAt`/`isExpired`) lives in `expiry.ts`, free of DB/S3/env imports so it is unit-testable without a running stack; the effect (`expireArchive`, the reaper loop, the admin release path) lives in `reaper.ts`.
* **Configuration**: `DOWNLOAD_ARCHIVE_TTL_DAYS` (default 5, `0` = never expire) and `DOWNLOAD_ARCHIVE_SWEEP_SECONDS` (default 3600) added to `.env.example`, `docker-compose.yml` (both API and worker), and `helm/pixshar/values.yaml` + `templates/configmap.yaml` (using `dig`, not `default`, so `0` isn't mistaken for "unset").
